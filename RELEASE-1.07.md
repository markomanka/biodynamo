# BioDynaMo 1.07: the ParaView export without ROOT's interpreter

*Release notes for the BioDynaMo consortium. The version is tagged `v1.07` on `master`, at the merge of the pull
request that records its validation on macOS (see *How it was tested*). It builds on
[version 1.06](RELEASE-1.06.md), whose notes remain the reference for the move to community-maintained
dependencies and for the new random numbers; this note lists only what changed since.*

*Marco Manca, with Claude (Anthropic). [SKUNKWORKS.md](SKUNKWORKS.md) describes the fork and its plan.*

## In short

BioDynaMo 1.07 is 1.06 with three changes that matter to users: the ParaView export works on current macOS,
because it no longer uses ROOT's interpreter; the `flocking` demo no longer reads uninitialized memory; and the
continuous integration is reorganized, with what it checks and leaves out written down in
[CI-COVERAGE.md](CI-COVERAGE.md). Interfaces for model code are those of 1.06, and no change alters the results
of a model, apart from the `flocking` demo described below.

## Why now

- **macOS.** conda-forge's ROOT 6.40.04 cannot read system headers with a macOS SDK of version 15 or newer; this
  was reported on 30 October 2026 as
  [root-feedstock#396](https://github.com/conda-forge/root-feedstock/issues/396) and had received no reply by
  17 November. Current versions of macOS and Xcode come without a 14 SDK. In 1.06 the ParaView export needed the
  interpreter while a simulation ran, so on such a Mac it did not work. Removing that need was planned for step 3
  of [SKUNKWORKS.md](SKUNKWORKS.md) and was brought forward for this reason.
- **Version numbers.** 1.06 was tagged on the branch `release/v1.06`, not on `master`, so builds of `master` made
  after it still reported version 1.05 plus a commit count (for example `1.05.278`). 1.07 is tagged on `master`
  itself, and later builds report 1.07 plus the number of commits since.

## What changes for users

### ParaView export

- The ParaView adaptor is registered by its library and loaded with `dlopen` instead of through ROOT's plugin
  manager (`VisualizationAdaptor::Register`). Other adaptor names still go to ROOT's plugin handlers.
- The arrays for exported data members are compiled into the library and chosen by the member's type, as ROOT's
  dictionary names it, instead of being generated by the interpreter for each simulation. Supported types are
  `real_t`, `int`, `uint64_t`, `AgentUid`, `AgentPointer`, and `MathArray` of `real_t`, `int` or `uint64_t` (such
  as `Real3`): the types the export could handle before. A data member of another type now stops the simulation
  with a message naming the member and its type, where the interpreter used to fail to compile. Only data
  members of classes that derive from `bdm::Agent` can be exported.
- On macOS the export works with the SDK the system provides; no 14 SDK is needed. `thisbdm.sh` and
  `thisbdm.fish` still warn about a too-new SDK, now only on behalf of the notebooks (see *Known issues*).
- The exported files are specified by a test that reads only the files (`ParaviewExportContractTest`), so that
  the later steps can change how they are written without changing what they contain.

### The `flocking` demo

`Boid::acceleration_accum_scalar` was read in the first step before it was ever set. When that memory held a
NaN, boids got the position NaN and the simulation crashed while placing agents on the grid; on Ubuntu 22.04
this happened in nearly every run of the CI. The demo now starts that value and its other scalars at zero, so
its results are defined and may differ from runs of 1.06 that did not crash. Its `bdm.json` also names the type
of `pos_gamma` so that ROOT finds it (`bdm::MathArray<double,3>`): before, the value 10000 was silently ignored
and the default used.

The uniform grid now checks each agent's position before placing it. An agent it cannot place stops the
simulation with its uid, type, position and diameter and the grid's bounds, instead of a segmentation fault.

### Installation

Configuring from an active conda environment that does not contain ROOT (for example Miniforge's `base`, or an
environment holding ParaView alone) now stops at once, with the two ways out: activate the environment created
from `environment.yml`, or choose the upstream method explicitly. Before, it fell back silently to the upstream
method and failed later; on macOS 26.7.1 this was reported on 23 November 2026 as "The link interface of target
\"ParaView::protobuf\" contains protobuf::libprotobuf, but the target was not found". An explicit
`-DBDM_SYSTEM_DEPENDENCIES` is respected, and nothing changes without an active conda environment.

### Continuous integration

[CI-COVERAGE.md](CI-COVERAGE.md) lists every workflow, what it checks, what it does not and why, and what must
be true before each gap is closed. The main changes since 1.06:

- Each pull request is checked once; pushes start the checks only on `master`. The only scheduled run is the
  Conda CI on macOS 26, weekly and by hand, which reports without blocking (the platform policy shared with
  [abm-io](https://github.com/markomanka/abm-io), in CI-COVERAGE.md).
- Ubuntu 22.04 is no longer tested, from 17 November 2026; the Ubuntu CI and the System CI run on 24.04 and
  26.04. Valgrind runs on 24.04 only. One failing system no longer cancels the others.
- The Ubuntu System CI (valgrind, every demo, the system tests and the notebooks) first ran in this fork on
  14 November 2026; it had been switched off by GitHub until then. What it found is recorded in CI-COVERAGE.md.
- On macOS every step uses the runner's active SDK, and the ParaView tests and an export from an installed copy
  run once more at the end, so that a return of the dependency on the interpreter fails the check.

## What does not change

Agents, behaviours, operations, the scheduler, diffusion, the neuroscience module, the random numbers
(Philox4x64-10, as in 1.06), checkpoints and the installation work as in 1.06. ROOT remains the I/O and
reflection layer, and the export still takes names, types and offsets from ROOT's dictionaries; step 3 replaces
them with generated field tables.

## Known issues

- **macOS, notebooks.** ROOT's notebook kernel interprets every cell with the same interpreter, so on macOS it
  still needs a 14 SDK (see INSTALL.md). It is not worked around: the notebooks move to the `xeus-cpp` kernel in
  step 2.
- **Linux, Abseil pin.** Unchanged from 1.06: `environment.yml` pins `libabseil=20260526` until conda-forge
  rebuilds ROOT ([root-feedstock#397](https://github.com/conda-forge/root-feedstock/issues/397)) or corrects the
  older ParaView builds ([paraview-feedstock#348](https://github.com/conda-forge/paraview-feedstock/issues/348)).
- **Not checked by the CI:** single precision (`-Dreal_t=float`), the demos other than `cell_division` with
  dependencies from conda-forge, GPU code, SBML, Spack, and macOS beyond the Conda CI job. CI-COVERAGE.md gives
  the reasons and the plan for each.
- **An occasional `pvbatch` abort** in `vtkXOpenGLRenderWindow::CreateAWindow` at the end of a demo was seen once
  in the CI (`multiple_simulations`, Ubuntu 24.04) and passed on a rerun.

## How it was tested

- The pull request that sets this version passed every check listed in CI-COVERAGE.md: the Conda CI on Ubuntu
  24.04 and macOS 15 with the active SDK and no 14 SDK, the Ubuntu CI and the Ubuntu System CI on 24.04 and 26.04,
  the Singularity integration and the repository checks.
- The Conda CI on macOS 26, started by hand on 21 November 2026 on `master`, passed.
- **By hand on macOS, by Aravind Raju**, on 25 November 2026, as CI-COVERAGE.md asks before each release: commit
  `8d83be3d` of `master`, macOS 26.7.1 (25G241) on Apple Silicon, SDK 15.4, Release build, dependencies from
  conda-forge (Python 3.14.10, ParaView 6.2.0, Protobuf 35.1.0, ROOT found in the environment). The build
  succeeded and the unit tests passed (CTest target `biodynamo-unit-tests`, 1/1, 111.77 s). Demos, system tests
  and notebooks were not part of this run. The commits between `8d83be3d` and the tag change documentation only.
- New tests since 1.06: what the ParaView export of agents must produce, what any way of loading adaptors must
  do, the grid's check of agent positions, and the logging and probability density helpers.

## Taking it

`v1.07` contains every change of `v1.06`. The one commit on `release/v1.06` that is not on `master` edited only
RELEASE-1.06.md and SKUNKWORKS.md. The adoption steps of RELEASE-1.06.md apply with `v1.07` in place of `v1.06`.
The ParaView changes touch only the visualization code and its tests, and the `flocking` changes only that demo
and the grid's check, so either can be taken alone.
